## 0. 结论速览

1. **`opt + fsr桥 + dlss5` 这一半已经跑通了**，而且是在**没有 XXMI** 的情况下跑通的。最新一局（`20261008-050834`，pid 242820）实机日志：
   - OptiScaler：`Upscalers.Dx11Upscaler: dlss`、`FrameGen.FGOutput: DLSSG`、`DLSSG.AdaMfgUnlock: true`、`DLSSG.InterpolationCount: 5`、`DLSS.RenderPresetForAll: 13`，`Dx11wDx12SC::Present`／`FGHooks::FGPresent` 全在跑。

   - 现在**唯一缺的就是 GIMI 模型替换**。

> **2026-10-08 06:05 更新（见 §11）**：有序注入链实测跑通，但**有 GIMI 在场必崩**（`CreateDXGIFactory1`、`0xC0000005`、`at=<no-module>`），
> 且查证 GIMI 从未成功初始化（无任何 3DMigoto 日志、`Mods` 为空）。因此内置链已**去掉 GIMI 这一环**，
> 先把 `桥 + OptiScaler + ReShade + DLSS5` 跑稳；GIMI 共存另开一条线。

2. **XXMI 报的 `无法检测到游戏进程 YuanShen.exe 的窗口`／`Failed to start game process` 是症状，不是原因。**
   游戏在 XXMI 把 `d3d11.dll` 注进去**之前约 0.15 秒就已经崩了**：`RenoDX-DLSS5-crash.log` 里 `[crash] pid=766348 up_ms=454 code=0xC0000005 (access-violation) DEP at 0x0 ... marks=attach:begin,ngx:hooks-installed,device:first-seen`。XXMI 的 30 秒等窗口等的是一个已经死掉的进程。

3. **"挂载顺序不对"的根因不是顺序表写错，而是同时存在两个互不隶属的注入者。**
   - Hub 侧：HoYoShade `inject.exe`、FSR Bridge 轮询注入器、以及（早期路径下）CreateProcess 阶段批量注入；
   - XXMI 侧：`core.utils.dll_injector`（`xxmi_dll_inject_mode = DIRECT`）。
   - 而 XXMI 手动模式起游戏用的是 `cmd.exe /c start`（见 `HoYoShadeHub_261008.log` L546-549），**父进程拿不到游戏句柄**，于是"谁先注进去"完全由三个轮询线程赛跑决定，代码层面无法定序。

4. **好消息：Genshin 从进程创建到第一次 `D3D11CreateDevice` 有约 4.4 秒的窗口**（工作局：批注入完成 `05:08:34.866`，首次 `D3D11CreateDevice` `05:08:39.220`）。序只要有**单一注入者**，4 秒多足够定死顺序。

5. **回答"是否要从 3dm 开始从头加载"：要，但"从头"的准确含义是——3DMigoto 必须是唯一注入链的第一个，而不是让 XXMI 去晚期注入它。** 两条可行路线见 §6。

## 2. XXMI / 3DMigoto 的装载机制（源码级，非猜测）

源码来源：本机 `D:\APPS\XXMI\Resources\Bin\XXMI Launcher.exe`（PyInstaller 冻结，Python 侧字符串已验证）＋ 前一轮会话已提取的 3DMigoto C++ 源码 `.xxmi_research/libs/`（即 XXMI 的 DLL fork）。

### 2.1 两种注入方式都是"进程已在跑"之后的晚期注入

| XXMI 配置 `xxmi_dll_inject_mode` | 实现 | 说明（EXE 内文案） |
|---|---|---|
| `DIRECT` | `WriteProcessMemory` + `CreateRemoteThread(LoadLibraryW)` | "more reliable but requires direct memory access" |
| `HOOK` | `SetWindowsHookEx`（全局 `WH_CBT`） | "less reliable, but potentially less prominent for anti-cheats" |
| `SKIP` | 不注入 XXMI DLL | "Skip XXMI DLL injection" |

- `InjectorLib__Injector.cpp`：`Inject(pid, dll, timeout)` 就是 `VirtualAllocEx`＋`WriteProcessMemory`＋`CreateRemoteThread(LoadLibraryW)`——**与 Hub 的 `DllInjector.InjectIntoHandle` 是同一个原语**。返回码：100 进程打不开 / 200 远程内存失败 / 400 建线程失败 / 500 超时 / **600 LoadLibrary 失败** / 700 未知。
- `HookLibrary(dll,&hook,&mutex)`：建 `Local\3DMigotoLoader` 互斥体（重名→100），**把 DLL 先 LoadLibrary 进 loader 自己进程**，要求导出 `CBTProc`（没有→300），然后 `SetWindowsHookEx(WH_CBT, CBTProc, module, 0)`（失败→400）。
  → 即 **HOOK 模式的 DLL 是在"游戏创建/激活窗口"那一刻才被系统映射进游戏进程的**，也就是设备、交换链都建完之后。**它比 DIRECT 更晚，不是更早。**

### 2.2 `DllMain` 的三道门（`DirectX11__DLLMainHook.cpp` L330-363）

```cpp
if (!verify_intended_target(hinstDLL)) return false;              // 门 1
if (hinstDLL != GetModuleHandleA("d3d11.dll")) HookD3D11(hinstDLL); // 门 2（返回值被忽略！）
if (FAILED(HookLoadLibraryExW())) return false;                   // kernel32，必过
if (FAILED(HookDXGIFactories())) return false;                    // 门 3：dxgi.dll 必须在！
```

- **门 1（准入）**：DLL 与 exe **同目录** → 直接放行；否则读自己旁边的 `d3dx.ini`，要么 `[Loader] loader` 等于当前 exe 文件名，要么 `target` 匹配 exe 路径后缀。GIMI 现在是 `loader = XXMI Launcher.exe`、`target = YuanShen.exe`。
  → 这条**同时解释了**：为什么在 Hub 进程里 `HookLibrary` 会返回 200（Hub 的 exe 既不叫 `XXMI Launcher.exe`，也不是 `YuanShen.exe`）。
- **门 2（是否装内联钩子）**：只有当自己**不是**进程里那个 `d3d11.dll` 模块时才装内联钩子（`D3D11CreateDevice` / `D3D11CreateDeviceAndSwapChain`）。**作为同目录代理被游戏加载时，这一支不执行**——那时它靠"我本身就是 d3d11.dll"转发。
- **门 3（硬门槛）**：`HookDXGIFactories()` 要 hook `dxgi.dll!CreateDXGIFactory{,1,2}`，**dxgi.dll 没加载 → `GetModuleBaseAddress` 返回 NULL → `DllMain` 返回 false → `LoadLibraryW` 返回 NULL → `Inject` 返回 600**。
  → 所以"很早就注入"并不天然可行：**注入时 dxgi 必须在**，而 d3d11 最好也已在（否则门 2 的内联钩子静默失败，只靠 2.3 的重定向兜底）。

### 2.3 晚期注入真正靠什么生效：`load_library_redirect`

`D3D11Wrapper.cpp` L1078-1101：`Hooked_LoadLibraryExW` 把游戏对 **`C:\Windows\system32\d3d11.dll` 的 `LoadLibraryExW`** 重定向到 **"3DMigoto DLL 自己所在的目录"**：

```cpp
// If we are loaded via injection we should load from directory
// where the 3DMigoto DLL resides rather than the game directory.
if (GetModuleFileName(migoto_handle, fullPath, MAX_PATH)) { ... wcscat(fullPath, library); ... }
```

生效条件（L1170）：`G->load_library_redirect > 1`。**GIMI 的 `d3dx.ini` 里 `load_library_redirect = 2`（L477），已满足。**
但——只 hook 了 `LoadLibraryExW`，**没有 hook `LoadLibraryW`**（源码 L1133 原话："It's not clear if we should also hook LoadLibraryW, but we don't have examples where we need that yet"）。

### 2.4 本游戏加载图形 DLL 的 PE 事实（本次实机解析）

| 模块 | 导入 d3d11 | 导入 dxgi | 导入 d3d12 | 备注 |
|---|---|---|---|---|
| `YuanShen.exe` | ✗ | ✗ | ✗ | 22 个导入里有 `OPENGL32.dll`、`USER32`… |
| `mhypbase.dll` | ✗ | **✓** | ✗ | 18 个导入 |

→ **`d3d11.dll` 不是静态导入的，是运行期动态加载；`dxgi.dll` 随 `mhypbase.dll` 进来。** 而 `mhypbase.dll` 也不在 `YuanShen.exe` 的静态导入表里，是更早一步动态加载的。
**推论（未直接实测）**：`CREATE_SUSPENDED` 挂起起进程的那一刻，`dxgi.dll` 极可能还没进进程 → 门 3 失败 → `Inject` 返回 600。这与仓库历史里"挂起注入 CLI 废弃（锚定失败）"（`a62433a`）的结论互相印证。

## 4. 对用户"理论顺序"的逐条修正

> 用户设想：原神启动 › dx11 › xxmi 挂载 dx11 › xxmi 完成 › fsr 桥接入 › opt 桥接 dlss › opt 开启帧生成 › opt 启动 dx12 进程 › reshade 注入 dx12 进程

| 设想 | 修正 |
|---|---|
| "xxmi 挂载 dx11 → xxmi 完成 → fsr 桥接入" | 方向正确：**3DMigoto 必须是最外层**（它和 Bridge/Opti 都在同一批函数上装钩子，谁先装谁是外层）。 |
| "opt 启动 dx12 进程" | **不存在新进程**。Opti 是在**同一个 YuanShen.exe 内**创建私有 D3D12 设备（`Dx11wDx12SC`、`D3D12CreateDevice`），靠共享句柄做 DX11↔DX12 互操作。 |
| "reshade 注入 dx12 进程" | 实际是**第二个 ReShade runtime 挂到 D3D12 侧交换链**（本机用 `ReShade2.ini`），不是注入新进程。 |
| 顺序里没提的 | `Dx11FsrBridge.autoload.txt` 表明 **OptiScaler 是 FSR 桥在自己进程内 LoadLibrary 起来的**，所以"桥接入"和"opt 桥接"不是两个独立注入步骤。 |
| 顺序里没提的 | ReShade 必须排在**最后**（现有代码注释：先注 ReShade 会先占住 d3d11，3DMigoto 再注就 600）。与本机 `GenshinEarlyLaunch.cs` L47-58 的 `[Bridge, FFX12, Opti, ReShade]` 一致。 |

## 6. 两条可行路线

### 方案 B（推荐，不动游戏目录）：**进程内驻留装载器**定序

> 2026-10-08 修正：本节初版写的是"Hub 在外部等 dxgi 落模块表后再重试注入"。**该设计已作废**，
> 原因见下方"为什么外部时序不可行"。正确形态是下文的**驻留装载器**。

**核心：在 CreateProcess 那一刻只外部注入一个我们自己的"装载器"，由它在进程内按序把其余层拉起来。**

```
第 0 步（外部，t≈0.05s，反作弊生效前）：只注入 1 个 loader.dll
  └ loader 只依赖 kernel32，必定成功；不需要 OpenProcess（复用 CreateProcess 的句柄）

第 1 步（进程内，由 loader 完成）：
  1. 持 Local\3DMigotoLoader 互斥体（3DMigoto 靠它判断"loader 在场"）
  2. 进程内轮询 GetModuleHandle("dxgi.dll")          ← 门 3 硬条件，微秒级延迟
  3. LoadLibraryW(D:\APPS\XXMI\GIMI\d3d11.dll)      ← 第 1 层：3DMigoto
  4. LoadLibraryW(<Dx11FsrBridge.dll>)              ← 第 2 层：桥（它自己 hook LoadLibrary 家族）
  5. 桥按 Dx11FsrBridge.autoload.txt 拉 OptiScaler   ← 第 3 层（现成机制）
  6. LoadLibraryW(<HoYoShade\ReShade64.dll>)        ← 最后
  7. 互斥体保持打开到游戏退出（否则下次 XXMI 报 100）
```

**为什么外部时序不可行（实测数据）：**

| 约束 | 数据 | 出处 |
|---|---|---|
| 3DMigoto 装载要求 dxgi.dll 已在 | `if (FAILED(HookDXGIFactories())) return false;` → `Inject` 600 | `DLLMainHook.cpp` L356-357 |
| 外部注入窗口 | ~1 秒（反作弊起来后拒 OpenProcess/VirtualAllocEx） | `GenshinEarlyLaunch.cs` 类注释 + `DllInjector.cs` L62-64 |
| **游戏建 D3D11 设备的时间本身在剧烈波动** | 一局是 `t+0.55s`（addon attach+454ms 就 `device:first-seen`），另一局是 `t+4.9s` | `RenoDX-DLSS5-crash.log` vs `shade-ReShade.log` L35 |

外部方案必须同时满足"dxgi 已到"∩"设备还没建"∩"反作弊窗口内"，而这三个区间**实测宽度不稳定**——
这正是历史上"六轮注入时序实验全部证伪"（`f951d48`）的根源。**进程内装载器把这个交集从"外部猜"变成"进程内等"，不再受前两个约束影响。**

**其他好处**：彻底消灭现在"HoYoShade inject.exe / Bridge 轮询器 / Hub extra 注入器 / XXMI dll_injector"四个轮询者赛跑。

**已核实的落地条件**：本机有 MSVC 14.44 + MSBuild（`D:\VS2022BuildTools`）；仓库已有原生工程 `src\HoYoShadeHub.Launcher\HoYoShadeHub.Launcher.vcxproj` 可参照。

**改动清单**：① 新增 loader DLL 原生工程；② `GenshinEarlyLaunch` 的批注入列表改为只注 loader；
③ `XxmiInjector.PrepareManualMode` 顺带写 `xxmi_dll_inject_mode = SKIP`（该键**不在** XXMI 签名保护名单，
被保护的只有 `unsafe_mode`/`run_pre_launch`/`custom_launch`/`run_post_load`/`extra_libraries`，故可外改）；
④ `GenshinLaunchRouting.UseEarlyGraphicsLaunch` 去掉 `!xxmiEnabled`，让勾了 XXMI 也走批注入路径；
⑤ 互斥体生命周期绑定游戏进程并在退出时释放。

**唯一未定项**：GIMI 与桥谁先。用户实测"先注 ReShade 会让 3DMigoto 注入返回 600"支持"3DMigoto 尽量靠前"；
但上游 3DMigoto 有一条相反方向的注释（社区调研引 `HookedDXGI.cpp:801-807`："3DMigoto getting in first was the fail case"）。
**本机 `.xxmi_research/libs/DirectXGI__DXGIWrapper.cpp` 是 2015 年的 logger 版，未找到该句**，需以 GIMI 实际带的
d3d11.dll 版本为准。→ **把加载顺序做成 loader 的可配参数，首次实测跑两组顺序对照。**

### 方案 A（确定性最强，但有游戏目录足迹）：经典 3DMigoto 代理布局

把 GIMI 的 `d3d11.dll` **放进游戏目录**，让 Windows 加载器在游戏启动时**第一个**把它作为 `d3d11.dll` 载入。

### 9.2 最终方案（B-3）：把定序链放进桥的 autoload

只外部注入 **1 个** DLL（桥），其余全在进程内、按固定顺序、在设备创建之前完成：

```
外部 t≈0.05s：Inject Dx11FsrBridge.dll        ← 唯一一次外部注入（1s 反作弊窗口内）
进程内（桥的 detached 线程）：
  1. CreateMutexW(Local\3DMigotoLoader) 并保持到进程退出
  2. 轮询 GetModuleHandleW(L"dxgi.dll")（5ms；3DMigoto DllMain 的硬门槛）
  3. LoadLibraryW(GIMI\d3d11.dll)              ← 第 1 层 3DMigoto（必须在 Opti/ReShade 之前）
  4. LoadLibraryW(OptiScaler.dll)              ← 第 2 层（现有 autoload）
  5. 轮询 OptiScaler 落模块表
  6. LoadLibraryW(HoYoShade\ReShade64.dll)     ← 最后（ReShade 必须在 GIMI 之后，用户实测 600）
```

**为什么这解决了"顺序"**：不再有第二个注入者、不再有轮询赛跑；顺序是代码里的先后调用；且每一步都在进程内，不受 1s 反作弊窗口和"设备可能在 0.55s 就建好"的影响。

**关于"谁在外层"的最终结论**（已把 §6 的"唯一未定项"收敛）：调用顺序上，内联钩子**后装者先被调用**（后装 = 外层），所以"GIMI 先加载"会让 GIMI 位于**内层**、Opti/桥在外层。这不影响功能：
- 加载顺序被"先注 ReShade/Opti → GIMI 返回 600"这条实测事实**锁死为 GIMI 必须在最前**（否则根本装不上）；
- 而模型替换只需要 GIMI 能看到/改写每一笔 draw，内层同样满足（游戏 → 外层钩子 → GIMI → 真驱动）；
- 帧生成需要 Opti/桥掌握最终 Present，外层正是它们该在的位置。

## §14 2026-10-08 崩溃定位：桥克隆的 Context 虚表少算 21 个槽（已修，待游戏内验证）

### 14.1 症状

链模式（桥 + GIMI）启动原神：进程退出码 `0xC0000005`，桥日志与探针文件里**没有任何 fatal 记录**，只有 `chain_done` 之后一片空白。

关键一条来自游戏自己的日志 `%USERPROFILE%\AppData\LocalLow\miHoYo\原神\output_log.txt`：

```
MultiThreadStackTrace init success!
Set new unhandled exception filter 00007FF737C81640 to replace 00007FF738DC4558
...
GfxDevice: creating device client; threaded=1
Direct3D:
    Version:  Direct3D 11.0 [level 11.1]
    Renderer: NVIDIA GeForce RTX 4060 Laptop GPU (ID=0x28e0)
**** Crash! ****
```

两点：**游戏自己把未处理异常过滤器换掉了**（所以桥的 `SetUnhandledExceptionFilter` 一条都没记到，不能据此判断"没有异常"）；**设备已经创建成功**，崩在紧随其后的那一步。

### 14.2 证据链（可复现）

1. 崩堆目录：`%TEMP%\mihoyocrash_<hash>\error.log`（UTF-16）：
   `YuanShen.exe caused an Access Violation (0xc0000005) ... RIP: 0x00000000`、`Write to location 00000000 caused an access violation.`
   `RSP: 0xb90fed68`，而 `Stack:` 段第一行 `0xb90fed68: 6b7cc994 00007ff9` —— 对 `call [空]` 来说栈顶就是调用方压入的返回地址。
2. 同目录 `output_log.txt` 的符号化栈回溯第一帧：
   `0x00007FF96B7CC994 (d3d11)`，而模块表里 `D:\APPS\XXMI\GIMI\d3d11.dll` 基址 `0x7FF96B720000`
   ⇒ 崩点在 **GIMI 的 d3d11.dll，RVA `0xAC994`**。
3. PE 节表：`.text VA=0x1000 Raw=0x400` ⇒ `RVA = 文件偏移 + 0xC00`，故 RVA `0xAC994` → 文件偏移 `0xABD94`。该处机器码：
   ```
   48 8B 01              mov  rax,[rcx]      ; rax = 接口指针的虚表
   ...
   FF 90 30 04 00 00     call qword ptr [rax+0x430]   ; 末尾正好停在被记录的返回地址 0xAC994
   ```
   ⇒ **一次虚函数调用，虚表第 `0x430/8 = 134` 号槽位是 NULL**。
4. 源码对照（`Dx11FsrBridge.cpp`）：
   - `k_context_vtable_size = 128`，`k_context4_vtable_size = 149`；
   - `clone_and_patch_vtable()` 用 `VirtualAlloc`（**零填充**）分配 `method_count` 个槽，`memcpy` 源虚表后把克隆指针写回对象的 vptr；
   - `context_vtable_size()` 只有在 `QueryInterface(ID3D11DeviceContext4)` **返回同一个指针**时才给 149，否则给 **128**。
   ⇒ 对象的 vptr 被换成一段只有 128 槽、**之后全为 0** 的内存；134 > 128，于是 `call [rax+0x430]` 读到 0 ⇒ RIP=0。

### 14.3 为什么基线没事、为什么 A（仅 GIMI）也没事

- 基线（只有桥一层包装）：游戏只调用自己认识的槽（<128），永远碰不到被截断的尾部，一切正常。
- A（只有 GIMI 一层包装）：GIMI 自己维护完整的 Context4 表，转发不经过桥的克隆。
- 桥 + GIMI 同时存在：GIMI 作为第二层包装，转发 Context4 方法（第 134 槽）时踩到桥克隆表的空洞 ⇒ `call 0`。

这类"少克隆"的坑，代码注释里已经为 swapchain 踩过一次（"Keep all inherited entries when cloning its vtable"），context 是漏网的那一个。

### 14.4 修复

`context_vtable_size()` 一律返回 `k_context4_vtable_size`（149），不再按 QI 结果回退到 128。多克隆的 21 项来自源虚表相邻数据，正常调用方不会调用它们；对基线**没有任何行为改变**（只是把原本为 0 的尾部换成真实相邻值）。context 的克隆只有这一处调用点（`install_context_hooks`），已确认覆盖。

### 14.5 顺带确认的事

- 桥在 B 局日志里是 `iat_scan create_device_and_swapchain_hooks=0 create_device_hooks=0` + 警告"未找到 d3d11 创建设备导入钩子" ⇒ 游戏的设备创建走的是 **GIMI 代理导出**，桥的设备钩子从未挂到这条路径上（所以探针 v5 里没有 `create_device_enter`）。
